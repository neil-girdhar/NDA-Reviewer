AI-Powered Project Workflows

Move beyond one-off prompts. Build persistent instruction files, workflow frameworks, and lessons-learned systems that scale across sessions and teams.

Advanced   Assumes prompting fundamentals   25-30 minute read

Beyond Single Prompts

Single prompts work well for isolated tasks — drafting an email, summarizing a document, analyzing a dataset. But real projects involve multiple sessions, evolving requirements, and accumulated knowledge. When you close a conversation and start a new one, the AI forgets everything.

This creates three problems that single prompts cannot solve:

ProblemWhat HappensSolution
Context loss Every new session starts from zero. You re-explain project conventions, file structures, and constraints each time. A persistent instruction file that the AI reads at the start of every session
Inconsistency Without shared rules, the AI makes different decisions in each session — different naming conventions, formatting, tone. A workflow framework with explicit principles the AI follows consistently
Repeated mistakes The AI makes the same error in session 5 that you corrected in session 2. There is no institutional memory. A lessons-learned system that captures corrections and prevents recurrence
The Three Pillars

This page teaches three tools that solve these problems: (1) an instruction file for persistent context, (2) a workflow framework with six principles for consistent execution, and (3) a lessons loop for continuous improvement. Together, they turn AI from a conversation partner into a project collaborator.

The Workflow Framework: Six Principles

These six principles form a reusable framework for managing AI-assisted projects. Each one addresses a specific failure mode that emerges when projects grow beyond single-session tasks. You can adopt them individually or as a complete system.

#PrinciplePrevents
1Plan FirstWasted effort from building the wrong thing
2Verify Before DoneBugs and incomplete work shipped as "finished"
3Capture LessonsRepeating the same mistakes across sessions
4Demand EleganceHacky solutions that create technical debt
5Stay AutonomousUnnecessary back-and-forth that slows you down
6Delegate Focused WorkContext window overload on complex problems

Expand each principle below to see the rules and how to apply them.

1. Plan First
Plan First

For any task with 3 or more steps or any architectural decision, write a plan before building. The plan should include goals, affected files, implementation steps, and a verification approach.

Rule: If something goes sideways during execution, stop and re-plan immediately. Do not keep pushing on a broken approach.

In practice: Before starting a multi-file project, ask the AI to outline its plan: what it will build, in what order, and how it will verify each piece. Review this plan before any code or content is created. A 5-minute plan review prevents hours of rework.

2. Verify Before Done
Verify Before Done

Never accept output as complete without proving it works. Run tests, check logs, review diffs, demonstrate correctness. The standard: would a senior professional approve this?

Rule: If you cannot verify the output yourself (e.g., it requires hardware you do not have), define what verification looks like and build automated checks where possible.

In practice: After the AI generates code, ask it to run the tests. After it writes a report, ask it to check that every claim has a supporting data point. Verification is not a final step — it is woven into every step.

3. Capture Lessons
Capture Lessons

After any correction, write down the pattern: what went wrong, why, and what rule prevents it next time. Review these lessons at the start of each session.

Rule: Write rules for yourself (or your AI) that prevent the same mistake. Iterate on these rules until the mistake rate drops.

In practice: Maintain a lessons file (e.g., lessons.md) alongside your project. Each entry has a date, context, what happened, and a concrete rule. When starting a new session, the AI reads this file and avoids known pitfalls. See Capturing Lessons for the full pattern.

4. Demand Elegance
Demand Elegance (Balanced)

For non-trivial changes, pause and ask: "Is there a more elegant way to do this?" If a solution feels hacky, step back and implement the clean version. But skip this for simple, obvious fixes — do not over-engineer.

Rule: Challenge your own work before presenting it. The question is not "does it work?" but "would I be proud of this solution?"

In practice: When the AI proposes a workaround, ask: "Knowing everything you know now, what is the elegant solution?" This often produces cleaner architecture than iterating on a patch.

5. Stay Autonomous
Stay Autonomous

When given a problem, resolve it. Point at logs, errors, and failing tests — then fix them. The goal: zero context-switching required from the person overseeing the work.

Rule: Do not ask for hand-holding on problems you can diagnose. Go fix failing tests without being told how.

In practice: Include this principle in your instruction file so the AI investigates and resolves errors rather than asking you what to do. If a build fails, the AI should read the error, identify the cause, and fix it — then report what it did.

6. Delegate Focused Work
Delegate Focused Work

For complex problems, break the work into focused sub-tasks. Each sub-task gets dedicated attention rather than competing for space in one long conversation. This keeps the main thread clean and prevents context overload.

Rule: One task per focused thread. Offload research, exploration, and parallel analysis so the main conversation stays on track.

In practice: When a project requires both research and implementation, do the research first in a separate conversation (or use sub-agents if your tool supports them). Bring the findings back to the main thread as a concise summary.

Portability

These six principles are tool-agnostic. Whether you use Claude, ChatGPT, Copilot, or another AI tool, the framework applies. The principles address human-AI collaboration patterns, not any specific tool's features.

Writing Your Instruction File

An instruction file is a persistent document that the AI reads at the start of every session. It replaces the need to re-explain your project conventions, file structure, and quality standards in every conversation. Think of it as onboarding documentation for the AI — the same way you would onboard a new team member.

The Four Sections

A well-structured instruction file has four sections:

  1. Project Context — What the project is, who it serves, and the current goal. This orients the AI so it makes decisions aligned with your objectives.
  2. Key Paths — Where source files, references, and outputs live. Prevents the AI from creating files in the wrong locations or guessing at directory structure.
  3. Conventions — Coding standards, formatting rules, naming patterns, style requirements. Everything the AI needs to produce output that matches your existing codebase or document style.
  4. Constraints — What NOT to do. Scope limits, quality gates, prohibited patterns. Constraints are often more powerful than instructions because they prevent entire categories of mistakes.

Example

Sample instruction file for a web application project 
# Project Instructions

## Project Context
- Internal dashboard for the operations team
- Stack: React + TypeScript frontend, Python FastAPI backend
- Current sprint goal: Add user role management

## Key Paths
| Purpose | Path |
|---------|------|
| Frontend source | src/frontend/components/ |
| Backend API | src/api/routes/ |
| Tests | tests/ (pytest for backend, vitest for frontend) |
| Database migrations | src/api/migrations/ |

## Conventions
- TypeScript: strict mode, no `any` types
- Python: type hints on all functions, docstrings required
- Components: one component per file, PascalCase naming
- API routes: snake_case, versioned under /api/v1/
- Commits: conventional commits format

## Constraints
- Do NOT modify the authentication middleware
- Do NOT add new dependencies without documenting why
- All API changes require corresponding test updates
- Keep bundle size under 250KB per chunk

Advanced Technique: Few-Shot Prompting

Few-shot prompting means providing 2-3 examples of input-output pairs before your actual request. Instead of describing the format you want in abstract terms, you show the AI exactly what correct output looks like. The AI then follows the pattern for your real input.

This is especially useful when the format is nuanced and hard to describe in words — for example, a specific classification scheme, a particular writing style, or a structured analysis pattern.

Example: Classifying Feedback

Without examples

Classify each customer comment as product, service, or billing.

The AI guesses at boundary cases. "The app crashed after I updated my payment method" — is that product or billing? Without examples, the AI decides inconsistently.

With few-shot examples

Classify each comment. Here are examples:

Comment: "The dashboard loads slowly."
Category: Product — Performance

Comment: "I was charged twice this month."
Category: Billing — Overcharge

Comment: "Support took 3 days to respond."
Category: Service — Response Time

Now classify these comments: [your data]

The AI follows the exact pattern: Category — Subcategory. Boundary cases are resolved by matching the closest example.

How many examples?

Two to three examples is the sweet spot. One example might be coincidence; four or more wastes tokens. Choose examples that show different categories and at least one boundary case. The AI learns format, tone, level of detail, and classification boundaries from your examples.

Advanced Technique: Self-Consistency Checking

Self-consistency checking means asking the AI to review, verify, or critique its own output before you accept it. Instead of trusting the first answer, you build a verification step directly into your prompt.

Three Approaches

Verify and Correct — for data and calculations

[After the AI produces analysis]

Now review your analysis. Check each calculation for accuracy. If you find any errors, correct them and explain what was wrong. Confirm that your conclusions follow logically from the data.

When to use: Financial analysis, data summaries, metric calculations — any task where numerical accuracy matters.

Argue Against — for recommendations

[After the AI recommends option B]

Now argue against your own recommendation. What are the strongest reasons to choose a different option? Are there risks you downplayed or benefits you overstated? After presenting the counterargument, state whether your original recommendation still stands and why.

When to use: Vendor evaluations, strategy decisions, any recommendation where confirmation bias could lead to a weak analysis.

Checklist Audit — for deliverables

[After the AI produces a document or code]

Audit your output against this checklist:
1. Does every section from the requirements appear?
2. Are all data points sourced and verifiable?
3. Is the tone consistent throughout?
4. Does the word count meet the constraint?
5. Are there any claims without supporting evidence?
Report your findings. Fix any issues you identify.

When to use: Complex deliverables with specific requirements — reports, documentation, code that must meet a spec.

Why This Works

AI models perform better when asked to verify their work because the verification step triggers a different reasoning path. The initial response optimizes for fluency and completeness; the verification step optimizes for accuracy and consistency. These two passes catch errors that a single pass misses.

Hands-On: Build a Comparison Report

Time to apply what you have learned. In this exercise, you will give an AI structured reference data, ask it to produce a self-contained HTML comparison report, and save the result as a file you can open in any browser. No development tools required — just your browser and Notepad.

Step 1: Gather Your Data

Every good comparison starts with structured reference data. Below is a context block with key properties for three common engineering materials. Copy this entire block — you will paste it into your AI prompt in the next step.

Material Data for Comparison:

Aluminum 6061-T6:
- Tensile Strength: 310 MPa (45 ksi)
- Yield Strength: 276 MPa (40 ksi)
- Density: 2.70 g/cm³
- Elastic Modulus: 68.9 GPa
- Corrosion Resistance: Good (forms protective oxide layer)
- Relative Cost: Medium
- Machinability: Excellent
- Weldability: Good (requires proper filler alloy)

A36 Structural Steel:
- Tensile Strength: 400–550 MPa (58–80 ksi)
- Yield Strength: 250 MPa (36 ksi)
- Density: 7.85 g/cm³
- Elastic Modulus: 200 GPa
- Corrosion Resistance: Poor (requires coating or painting)
- Relative Cost: Low
- Machinability: Good
- Weldability: Excellent

304 Stainless Steel:
- Tensile Strength: 515 MPa (75 ksi)
- Yield Strength: 205 MPa (30 ksi)
- Density: 8.00 g/cm³
- Elastic Modulus: 193 GPa
- Corrosion Resistance: Excellent (chromium oxide passive layer)
- Relative Cost: High
- Machinability: Fair (work hardens)
- Weldability: Good (low carbon grade preferred)

Where does this data come from?

These are commonly referenced properties from engineering handbooks. In a real project, you would substitute values from your company’s approved material specifications, supplier data sheets, or resources like MakeItFrom.com. You can also upload PDF data sheets directly if your AI tool supports file attachments.

Step 2: Write the Comparison Prompt

Now paste the data block above into your AI tool, followed by this prompt. The key technique: you are telling the AI exactly what output format you want and where to save it — a complete, self-contained HTML file written directly to disk.

Using the material data I provided above, create a self-contained HTML comparison report and save it as comparison.html on my desktop.

The report should include:
1. A title and brief introduction explaining the purpose of the comparison
2. A comparison table with all properties side by side for all three materials
3. Color-coded cells: green background for best-in-category, red background for worst-in-category
4. A "Best For" summary section explaining which material suits which application type
5. Clean, professional styling using inline CSS (no external stylesheets or scripts)

Make the HTML complete and valid so I can open comparison.html directly in my browser.

How you get the file depends on your tool

IDE-integrated AI (Claude Code, Cursor, Copilot Chat): The tool writes comparison.html directly to your project folder. Just open it.
Web-based AI (claude.ai, ChatGPT): The AI shows you HTML code in the chat. You will need to copy it and save the file yourself. See the steps below.

How to save HTML from a web-based AI chat
  1. Copy the AI’s entire HTML output (everything from <!DOCTYPE html> to </html>)
  2. Open Notepad (search “Notepad” in the Windows Start menu)
  3. Paste the HTML into Notepad
  4. Go to File → Save As
  5. Change the filename to comparison.html
  6. Important: Change the “Save as type” dropdown from “Text Documents (*.txt)” to “All Files (*.*)”
  7. Click Save, then double-click the file to open it in your browser

If you skip step 6, Windows saves the file as comparison.html.txt and it opens as plain text instead of a styled report.

Step 4: Verify and Refine

Apply the self-consistency checking technique from the previous section. Paste this follow-up prompt to have the AI audit its own work:

Review the HTML comparison report you just created against the original material data I provided. Check that:

1. All property values in the table exactly match the source data
2. The color coding is correct (green = best in each row, red = worst in each row)
3. The "Best For" recommendations are consistent with the property data
4. The HTML is valid and will render correctly as a standalone file

If you find any errors, explain what was wrong and provide the corrected complete HTML.

This is Verify Before Done in action — never accept the first output without checking it against your source data.

The Project Lifecycle

Here is a seven-step lifecycle for running an AI-assisted project. Each step integrates the workflow principles from the framework above. Walk through each phase to see what happens and which principle applies.

1. Define Scope & Create Workspace

Before opening an AI tool, define what you are building. Set up a folder structure with clear locations for source files, references, and outputs.

Example structure:

my-project/
  instructions.md    ← your instruction file
  lessons.md         ← captured corrections
  references/        ← specs, data, templates
  src/               ← source code or content
  output/            ← build artifacts

Principle applied: Plan First — Define the workspace before any AI interaction. This 5-minute setup prevents hours of file-location confusion.

2. Write Your Instruction File

Create your instruction file with the four sections: Project Context, Key Paths, Conventions, and Constraints. Include the workflow principles you want the AI to follow.

This file persists across sessions. At the start of each conversation, tell the AI to read it: "Read instructions.md and follow all conventions."

Principle applied: Plan First + Capture Lessons — The instruction file is your upfront plan. As lessons accumulate, update the Constraints section to prevent recurring issues.

3. Write Your First Project Prompt

Your first prompt should reference the instruction file and describe the deliverables. Two approaches:

  • Direct prompt (fast iteration) — Type the task directly in the conversation. Best for exploratory work.
  • Prompt file (maximum control) — Write the prompt in a file and tell the AI to read it. Best for complex requirements or team projects where the prompt needs review.

Read instructions.md and the requirements in references/spec.md. Build the following deliverables in this order:
1. Database schema (src/schema.sql)
2. API endpoints (src/api/)
3. Unit tests (tests/)
4. README with setup instructions

Follow all conventions in instructions.md. After each deliverable, verify it works before moving to the next.

4. Review the Plan

Before the AI starts building, ask it to present its plan. Verify:

  • Does the scope match your requirements? Nothing added, nothing missing?
  • Does the file structure follow your instruction file conventions?
  • Does the plan include testing and verification steps?
  • Is the build order logical? (Dependencies built before dependents.)

Principle applied: Plan First — A 5-minute plan review here prevents 2 hours of rework later. If the plan is wrong, redirect now — not after 500 lines of code exist.

5. Execute and Monitor

Let the AI build according to the approved plan. Monitor for:

  • Scope drift — Is the AI adding features you did not request?
  • Convention violations — Are file paths, naming, and formatting matching your instruction file?
  • Context limits — For long sessions, watch for signs that the AI is losing earlier context.

Principle applied: Stay Autonomous + Demand Elegance — The AI should resolve errors it encounters without asking you how. If a solution looks hacky, ask: "Is there a more elegant approach?"

6. Verify Results

Before accepting any deliverable as complete:

  • Run all tests. If tests fail, fix them before moving on.
  • Review the diff — what changed from the starting state?
  • Check edge cases the AI might have missed.
  • Ask yourself: "Would a senior professional approve this?"

Principle applied: Verify Before Done — This is the principle that catches the most issues. Never mark a task complete without demonstrating correctness.

7. Iterate and Capture Lessons

If verification reveals issues, report them specifically: what is wrong, where, and what the expected behavior should be. After the AI fixes the issue:

  1. Commit the working state — Save your progress so you can roll back if needed.
  2. Capture the lesson — If the issue was a pattern (not a one-off typo), add it to your lessons file. Include: what happened, why, and the rule that prevents it.
  3. Update your instruction file — If the lesson represents a new convention or constraint, add it to instructions.md so future sessions inherit the fix.

Principle applied: Capture Lessons — This is how projects get better over time. Each correction makes the next session smoother.

Capturing Lessons: The Self-Improvement Loop

The most powerful pattern in AI-assisted project work is the lessons loop. Every correction you make to AI output is an opportunity to prevent that mistake permanently. Without a lessons file, you correct the same issues in every session. With one, each session starts smarter than the last.

The Pattern

  1. Correction happens — You notice the AI did something wrong and you fix or redirect it.
  2. Document the pattern — Write an entry in your lessons file: date, context, what went wrong, and a concrete rule.
  3. Update instruction file — If the lesson is project-wide, add it as a constraint in your instruction file.
  4. Review at session start — At the beginning of each new session, the AI reads the lessons file and avoids known pitfalls.

Example Entry

## Button Styling Regression

**Date:** 2026-02-28
**Context:** AI changed a shared CSS class to fix one component,
which broke button styling on three other pages.

**Problem:** The AI modified `.btn-primary` globally instead of
creating a component-specific override.

**Rule:** Never modify shared CSS classes. Create a component-
specific class that extends the shared one. Always check which
other components use a class before changing it.
The Compound Effect

A lessons file with 10 entries prevents 10 categories of mistakes across every future session. After a few weeks of active use, the AI's effective error rate drops dramatically — not because the AI improved, but because your instruction system improved. This is institutional knowledge that persists even when team members change.

Keep entries actionable

A good lesson ends with a concrete rule the AI can follow. "Be more careful with CSS" is too vague. "Never modify shared CSS classes; create component-specific overrides instead" is a rule the AI can enforce consistently.
